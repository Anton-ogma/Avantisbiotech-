# Решения по ТЗ

Журнал решений по открытым вопросам к
[ТЗ «Постуральный модуль DIERS v1.0»](./TZ-postural-module-v1.0.md).

Разделы 4–12 ТЗ — контракт данных и алгоритмов, меняются только через ревью (§0).
Каждое изменение этих разделов фиксируется здесь: вопрос, решение, что именно
поправлено в тексте ТЗ, какие следствия за собой тянет.

Открытых вопросов не осталось: Р-1…Р-9 закрывают В-1…В-9, Р-10…Р-12 — конфликты К-1…К-3
из [сопоставления](./gap-analysis.md).

Часть решений расширяет ТЗ сверх заданного вопроса — новые значения, поля, эндпоинты.
Такие места помечены **⚠ расширение** и подлежат отдельному подтверждению: их можно
отменить, не трогая остальное.

## Р-1 · Состояние сессии — одно поле

**Дата:** 2026-08-16
**Вопрос:** В-1 — §4 задавал `sessions.status ∈ {draft, ready, analyzed, reported}`,
§8.1 — машину `prepared → … → analyzed`. Два словаря на одну сущность.

**Решение:** одно поле. Домен `sessions.status` — машина состояний §8.1;
прежний набор `draft|ready|analyzed|reported` упразднён.

**Итоговый домен (8 значений):**

```
prepared → baseline_recorded → probes_running → imported
  → quality_reviewed → shortlist_confirmed → analyzed → reported
```

`reported` перенесён из старого домена как терминальное состояние — §8.1
заканчивалась на `analyzed`, но выпуск отчёта состоянием сессии остаётся.

**Соответствие старых значений новым:**

| Было (§4) | Стало |
|---|---|
| `draft` | `prepared` |
| `ready` | `shortlist_confirmed` |
| `analyzed` | `analyzed` |
| `reported` | `reported` |

**Правки в ТЗ:**
- §4, таблица `sessions`: домен `status` заменён на машину §8.1, поле объявлено `not null`;
- §4: добавлено поле `low_confidence boolean default false`;
- §8.1: машина дополнена терминальным `→ reported`, зафиксированы односторонность
  переходов, запись в `audit_log` и разграничение с `reports.status`.

**Следствия:**

1. **`low_confidence` — отдельное поле, не значение статуса.** §8.2 требует помечать
   сессию при дрейфе нейтрали выше порога. Признак ортогонален стадии: помеченная
   сессия продолжает движение по машине до `reported`. Значением статуса он быть
   не может, поэтому вынесен в отдельную колонку. *Это добавление к схеме — если
   предполагалось иное место хранения, скажите.*

2. **Снята перегрузка слова `draft`.** До решения `draft` означал одновременно раннюю
   стадию сессии (§4) и неподписанный вывод (§1). Теперь `draft`/`signed` — только
   про отчёт, в `reports.status`; у сессии такого значения нет.

3. **`prepared` — начальное значение при вставке.** Поле `not null`, значения по
   умолчанию на уровне БД ТЗ не задаёт; `POST /sessions` (§13) создаёт сессию
   сразу в `prepared`.

4. **Переходы односторонние.** Возврат назад по машине схемой не предусмотрен;
   если понадобится (например, доснять пробу после `imported`), это отдельное
   решение — сейчас такой сценарий не описан.

**Открыто после решения:** нужен ли явный переход `analyzed → reported` в API.
→ Закрыто в [Р-7](#р-7--эндпоинты-переходов-состояния): добавлен
`POST /analyses/{id}/report`.

## Р-2 · Переанализ при смене версий

**Дата:** 2026-08-16
**Вопрос:** В-2 — §12 требует совпадения версий для сопоставимости, значит любое
обновление норм разрывает историю; сырые данные сохраняются, но эндпоинта переанализа
в §13 нет.

**Решение:** переанализ — штатная операция, а не аварийное восстановление.

1. `analyses` — только на вставку. Переанализ создаёт **новую** строку; прежние
   сохраняются навсегда (инвариант §4.5).
2. `POST /sessions/{id}/analyze` принимает необязательный набор версий. Без него —
   активная конфигурация, с ним — считает по указанной.
3. Добавлен `POST /patients/{ref}/reanalyze {versions, session_ids?}` — пересчёт курса
   под общий набор версий, асинхронно через очередь (§3), возвращает `job_id`.
4. **Сверка сопоставимости идёт по `analyses`, а не по `sessions`.** Версии в `sessions` —
   что действовало при обследовании; версии в `analyses` — с чем посчитали. Без этого
   разделения переанализ бессмысленен: сравнивались бы исторические версии, а не
   фактически применённые.
5. `GET /patients/{ref}/history` по умолчанию берёт **самый свежий набор версий,
   доступный для всех сессий пациента**, и печатает его рядом с графиком. Это
   превращает §12 из ограничения в рабочее правило: история остаётся связной, пока
   для сессий существует общий пересчёт.

**Подписанные отчёты не затрагиваются.** Отчёт привязан к своей строке `analyses`
(§4). Переанализ не отменяет и не переписывает подписанное заключение — это требование
воспроизводимости §1/§15, а не деталь реализации.

**Правки в ТЗ:** §4 (комментарий к `analyses`, инвариант 5), §12 (сверка по `analyses`,
подбор набора версий), §13 (`versions` у analyze, `reanalyze`, `?versions=` у history).

⚠ **расширение:** эндпоинт `POST /patients/{ref}/reanalyze` и параметр `?versions=`
в истории — сверх исходного §13.

## Р-3 · Пять версий конфигурации

**Дата:** 2026-08-16
**Вопрос:** В-3 — инвариант §4.2 перечисляет три версии, но `W_domain` из «профиля
клиники» (§9.2) в них не входит, значит смена весов меняет `result` при неизменном
`input_hash`.

**Решение:** пять версий вместо трёх. Добавлены `profile_version` и `registry_version`.

| Версия | Что покрывает | В `input_hash` | В сопоставимости §12 |
|---|---|---|---|
| `norms_version` | нормы (mean, sd, страты) | да | да |
| `thresholds_version` | SDC, `thresholds.PI` | да | да |
| `profile_version` | `W_domain`, `w_p`, `z_cap`, границы категорий z | да | да |
| `registry_version` | `param_registry`: домен, единица, направление, участие в PI | да | да |
| `rules_version` | правила рекомендаций | да | **нет** |
| `protocol_version` | реестр проб: `settle_sec`, `carryover_min` | нет | нет |

Обоснования разнесения:

- **`registry_version` понадобился из того же соображения, что и профиль.** §7 задаёт
  реестр параметров, но версии ему не давал. Смена домена параметра, его направления
  или участия в PI меняет результат при тех же измерениях — ровно та же дыра в
  детерминизме, про которую вопрос.
- **`rules_version` не входит в сопоставимость.** Правила влияют на рекомендации, а не
  на измеренные величины; иначе обновление библиотеки упражнений рвало бы историю
  постуральных показателей без всякой причины.
- **`protocol_version` не входит в `input_hash`.** Реестр проб определяет, как
  обследование проводится, а не как считается: на арифметику по уже собранным
  каноническим данным он не влияет. Поле в `sessions` уже было.

**Правки в ТЗ:** §4 (`sessions`, `analyses`, инвариант 2), §7 (версионирование реестра),
§10 (файлы `profiles/` и `registry/`), §12 (состав проверки).

⚠ **расширение:** `registry_version` — сверх заданного вопроса; вопрос был про веса.

## Р-4 · Порядок вердиктов комбинированной пробы

**Дата:** 2026-08-16
**Вопрос:** В-4 — `additive` и `dominant` могут выполниться одновременно, приоритет
в тексте задан неявно.

**Решение:** порядок проверки объявлен нормативным, первое совпадение выигрывает:

```
conflict → synergistic → dominant → additive → indeterminate
```

- **`conflict` первым.** Комбинация хуже лучшего одиночного уровня остаётся конфликтом,
  даже если численно совпала с суммой. Это безопасная сторона: §11 MUST запрещает при
  конфликте назначать оба уровня.
- **`dominant` раньше `additive`.** Пересечение возникает, когда вклад одного уровня
  в пределах шума. Честная формулировка для такого случая — «работает один уровень»,
  а не «вклады сложились»: вторая подсказывает врачу назначить оба.
- **`synergistic`** — комбинация лучше суммы одиночных, `ΔPI(AB) < add − thr`.
  В исходном тексте случай не назван, а он клинически самый интересный.
- **`indeterminate`** — не совпало ничего. Не интерпретируется, в рекомендации не идёт,
  требует повтора пробы. Без этого значения движку правил пришлось бы гадать.

**Правки в ТЗ:** §9.7 полностью переписан.

⚠ **расширение:** два новых значения вердикта — `synergistic`, `indeterminate`.

## Р-5 · Два списка вместо ранжирования по модулю

**Дата:** 2026-08-16
**Вопрос:** В-5 — топ-2 по `|ΔPI|` ставит ухудшающую пробу в конкуренцию с улучшающей.

**Решение:** ранжирование по модулю отменено, вводятся два раздельных списка.

- **`shortlist`** — только достоверные улучшения (`ΔPI < −thresholds.PI`), сортировка
  по величине улучшения. Подтверждающий повтор (§8.3) применяется к топ-2 из этого списка.
- **`notable_worsening`** — только достоверные ухудшения (`ΔPI > +thresholds.PI`).
  Печатаются в отчёте и в режиме тренера (§14.5 прямо требует показывать конфликты —
  они меняют выбор упражнений), но в рекомендации не попадают никогда и подтверждающим
  повтором не проверяются, помечаются `unconfirmed`.

Ухудшение диагностически ценно, но кандидатом в терапию не является — смешивать их
в одном ранжированном списке нельзя. Повтор ухудшающих проб не делается сознательно:
это удваивает длительность сессии ради данных, которые всё равно не станут назначением.

Пробы внутри полосы шума не попадают ни в один список — прямое следствие §9.3.

**Правки в ТЗ:** §8.3 переписан.

⚠ **расширение:** список `notable_worsening` как отдельная сущность результата.

## Р-7 · Эндпоинты переходов состояния

**Дата:** 2026-08-16
**Вопрос:** В-7 — §8.1 делает `quality_reviewed` и `shortlist_confirmed` обязательными
шагами с решением врача, но эндпоинтов для них в §13 нет.

**Решение:** переходы разделены на два типа.

**Неявные** — срабатывают по факту появления данных, отдельного вызова не требуют:

| Переход | Триггер |
|---|---|
| `prepared → baseline_recorded` | импортирована первая проба-нейтраль |
| `→ probes_running` | импортирована первая не-базовая проба |
| `→ imported` | очередь разбора пуста, нераспознанных файлов нет |

**Явные** — требуют решения человека, каждый пишется в `audit_log`:

```
POST /sessions/{id}/quality-review   {decisions: [{measurement_id, verdict, reason}]}
POST /sessions/{id}/shortlist        {confirmed_probe_codes[]}
POST /sessions/{id}/analyze          {versions?}
POST /analyses/{id}/report           {variant}
```

Последний закрывает вопрос, оставшийся открытым после Р-1: `analyzed → reported`
делает выпуск отчёта. `POST /analyses/{id}/sign` относится к отчёту (`reports.status`)
и состояние сессии не меняет.

**Правки в ТЗ:** §13 (три новых эндпоинта, разделение типов переходов).

⚠ **расширение:** три эндпоинта и разделение переходов на явные и неявные.

## Р-8 · Историзм `neutral_definition`

**Дата:** 2026-08-16

## Р-9 · Требования к `patient_ref`

**Дата:** 2026-08-16
**Вопрос:** В-9 — кто владеет соответствием `patient_ref ↔ учётная запись` и где ключ,
если §15 требует держать его вне модуля.

**Решение:**

1. Таблицу соответствия ведёт **хост**; модуль её не хранит и за identity к хосту
   не обращается.
2. `patient_ref` **непроизводен от ПДн** и **неперечислим**: UUIDv4 либо HMAC от
   идентификатора хоста с ключом, хранящимся у хоста.
3. Последовательные идентификаторы хост-системы в этой роли запрещены. Псевдоним вида
   `user_id = 42` не является обезличиванием: он перечислим и тривиально сопоставим
   с профилем в хост-системе, из-за чего требование §15 об обезличенном экспорте
   когорты перестаёт выполняться.

**Правки в ТЗ:** §13 (MUST к `patient_ref`), §15 (ссылка на требования).

## Р-10 · Язык домена и граница с хостом

**Дата:** 2026-08-16
**Вопрос:** К-1 — §3 запрещает смешивать домен между языками и требует Python-сервис,
если хост на другом языке; хост `fitmed-ecosystem` написан на TypeScript.

**Решение:** применяется предусмотренный §3 вариант. Модуль — отдельный Python-сервис
со своей БД, разворачивается самостоятельно, хост обращается к нему только по §13.
Существующий TS-модуль DIERS в fitmed целевым не становится и в кодовую базу модуля
не переносится.

Альтернатива — переписать §3 под TypeScript — отвергнута: §16 требует property-тестов
знаковых соглашений, табличных тестов алгоритмов и обработки сигнала ЭМГ
(фильтрация, спектральная интерполяция, MDF), а §3 предполагает аналитические ноутбуки
на тех же моделях данных. Ради переиспользования модуля, который по Р-11 всё равно
подлежит замене, менять стек не стоит.

**Правки в ТЗ:** §3, уточнение после правила о выносе домена.

## Р-11 · Владение данными пациента

**Дата:** 2026-08-16
**Вопрос:** К-2 — в существующей системе исследование принадлежит учётной записи
пациента: он сам создаёт, редактирует и удаляет свои данные. ТЗ строит клинический
инструмент.

**Решение:** пациент не является субъектом записи в модуль. Данные вводит `operator`,
выводы подписывает `clinician`. Пациент получает результат только пациентским вариантом
подписанного отчёта (`variant=patient`) и не имеет ни записи, ни удаления. Роль `coach` —
чтение своего варианта отчёта без доступа к сырым величинам (§14.5).

Удаление пациентом несовместимо с аудитом (§15) и воспроизводимостью (§4): подписанное
заключение обязано оставаться проверяемым, а исходные данные под ним — существовать.

**Последствие за пределами модуля:** сценарий «пациент ведёт свои исследования сам»,
работающий в fitmed, в целевой системе не воспроизводится. Это продуктовое изменение,
а не техническое, — если оно нежелательно, решение нужно пересмотреть до Этапа 1.

**Правки в ТЗ:** §15 (MUST о ролях записи).

⚠ **расширение:** решение меняет продуктовую модель, а не только схему прав.

## Р-12 · Что такое myoline

**Дата:** 2026-08-16
**Вопрос:** К-3 — в §9.8 myoline это изометрическая сила, не участвующая в анализе проб;
в существующей системе таблица `myoline_studies` хранит ЭМГ в мкВ.

**Решение:** термин закрепляется за изометрической силой, как в ТЗ. ЭМГ — отдельная
модальность со своими таблицами (§4). Унаследованные данные `myoline_studies` по
существу являются ЭМГ и при любой миграции трактуются как ЭМГ, а не как myoline.

ТЗ не меняется по существу — меняется трактовка legacy-данных. Обратный вариант
(признать myoline синонимом ЭМГ) отвергнут: он сломал бы MUST §9.8 о неучастии myoline
в анализе проб, а это содержательное методическое требование, а не вопрос именования.

**Правки в ТЗ:** §9.8, примечание о трактовке legacy-данных.
