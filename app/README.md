# Постуральный модуль DIERS — приложение

Реализация [ТЗ v1.0](../docs/diers/TZ-postural-module-v1.0.md) с решениями Р-1…Р-35.
Научно-практическая платформа: **выявляет закономерности, а не применяет готовые**.

```bash
make install && make dev     # http://localhost:5173, API на :8000/docs
make test                    # 68 тестов, таблица приёмки §16
make up                      # on-prem: docker compose
```

---

## Что реализовано

| Этап ТЗ | Состояние |
|---|---|
| **1. Скелет данных** | полностью: реестр параметров, знаковые соглашения, парсеры formetric/pedoscan, идемпотентный импорт, канонизация, Δ от нейтрали |
| **1.5. Повторяемость** | полностью: ICC(2,1) с ДИ, SEM, SDC, CV, паспорт параметра, разброс между операторами, калькулятор мощности |
| **2. Протокол** | план сессии, машина состояний с проходами, 11 валидаторов по матрице, рандомизация с seed, sham, слепой разбор, шорт-листы, отклонения от плана; аналитика протокола |
| 3–5. Bridge Agent, ЭМГ, кондилография | **не реализованы**: требуют реальных файлов экспорта как фикстур (§5.2 MUST) |
| 6. Движок правил | **не реализован** намеренно: в режиме `research` он выключен (Р-19), а `clinical` требует РУ |
| 7. Когортный слой | ядро есть: когорты с lockbox, предрегистрация, FDR, многомерный тест, оси отклика |

**Подпись УКЭП** реализована как контракт с проверкой хэша документа и метки времени;
криптопровайдер (КриптоПро) подключается на месте — в контейнере его нет.

## Архитектура

```
packages/
  domain/       чистые функции: config · indices · drift · effects · protocol ·
                reliability · stats · analysis · hashing
  importers/    formetric-csv-v4 · pedoscan-csv-v2, выбор через detect()
  contracts/    Pydantic v2 — единственный источник типов
  config/       registry · profiles · thresholds · norms · probes (YAML, версионируются)
apps/
  api/          FastAPI: routers · services · models · security
  worker/       ARQ: автопереанализ при публикации конфигурации
  web/          React + TS + Vite, SVG-графика без внешних библиотек
db/migrations/  партиционирование, права на audit_log, индексы
tests/          68 тестов: фикстуры · знаки · алгоритмы · протокол · детерминизм · API
```

**Граница жёсткая:** `packages/domain` не обращается к БД, сети и системным часам.
Всё приходит аргументами — поэтому расчёт детерминирован и покрыт табличными тестами.

## Что стоит посмотреть в первую очередь

**`packages/domain/indices.py`** — два индекса. `PI` требует норм, `RI` не требует.
Норм для этой комбинации оборудования не существует, и это не аварийное состояние:
`PI` возвращает `None`, `RI` работает в полном объёме, интерфейс печатает прочерк.

**`packages/domain/effects.py`** — `direction=unknown` по умолчанию. Параметр, по
которому закономерность не установлена, входит в индекс по модулю, но знака не
получает. Отклик, где ни один достоверно изменившийся параметр не имеет направления,
попадает в отдельный список `responsive_unsigned`: величина есть, знака нет.
Отправить его в «ухудшение» значило бы предрешить результат.

**`packages/domain/drift.py`** — дрейф нейтрали в единицах SDC, без участия обоих
индексов. Через `PI` считать нельзя (требует норм), через `RI` тоже (он сам определён
относительно нейтрали). Линейная часть корректируется, флаг ставится по остатку.

**`packages/domain/protocol.py`** — валидаторы полноты работают на утверждении плана,
до первой пробы. Проверка, срабатывающая на выходе из `probes_running`, ничего не
предотвращает: пациент уже ушёл.

**`packages/domain/stats.py`** — многомерный тест рядом с одномерными. Когда эффект
есть во многих параметрах, но каждый у порога, поправка на множественность гасит все,
а совместный тест — нет. Проверено `tests/test_stats.py`, там же тест калибровки
нулевой гипотезы.

## Масштабирование

Порядок величин: 1 млн пациентов × ~2 сессии в год × ~10 проб × ~20 параметров
≈ 400 млн строк витрины в год. Нагрузка на запись небольшая и предсказуемая,
тяжёлое — когортная аналитика.

| Решение | Зачем |
|---|---|
| API без состояния, `replicas` | инстансы взаимозаменяемы, масштабируются линейно |
| pgbouncer в transaction-режиме | узкое место не строки, а коннекты: 5000 клиентских на 50 серверных |
| Партиционирование по датам | отсечение партиций делает квартальный срез дешёвым при любом объёме |
| Витрина `param_values` | «все пациенты со значением выше X» по JSONB — полный перебор |
| `UNIQUE (session_id, input_hash)` | автопереанализ при неизменной конфигурации не создаёт строк вовсе |
| Конфигурации кэшируются по версии | они неизменяемы в пределах версии; пять справочников на каждый анализ читаются с диска один раз |
| Тяжёлое — в ARQ | разбор файлов и переанализ не живут в HTTP-запросе |
| `X-Request-Id` + `Server-Timing` | без корреляции по запросу разбор инцидента на десятке инстансов невозможен |

## Ограничения

**Пороги в поставке — `demo`.** Любые суждения о значимости на них недействительны,
и это печатается баннером на каждом экране. Продуктовые значения выпускает режим
повторяемости (Этап 1.5) из собственного test-retest.

**Норм нет.** Штатное состояние: работает `RI`, `PI` не вычисляется.

**Демо-данные синтетические.** `make seed` создаёт 6 пациентов с полным протоколом,
включая sham и подтверждающий повтор — чтобы экраны показывали смысл, а не заглушки.

**Криптопровайдер не подключён.** Подпись проверяется на уровне контракта: хэш
документа, метка времени, неизменяемость подписанного. Проверка самой УКЭП —
интеграция с КриптоПро на месте установки.
