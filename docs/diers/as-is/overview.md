## 1. Назначение и границы модуля

### 1.1 Назначение

Модуль хранит, отображает и сравнивает во времени результаты инструментальных
исследований опорно-двигательного аппарата, снятых на оборудовании
**DIERS International**:

- **DIERS formetric 4D** — оптическая (безлучевая) 3D/4D-топография спины:
  параметры позвоночника, постуры, походки;
- **DIERS Myoline** — поверхностная ЭМГ мышц туловища и ног
  (в коде идёт единым модулем-соседом, вторая вкладка того же экрана).

Клиническая задача: показать врачу и пациенту динамику «до / после» курса
лечения или реабилитации — не единичный снимок, а **траекторию** параметров.

### 1.2 Что модуль делает

1. Хранит исследования, привязанные к пациенту (`user_id`).
2. Принимает данные тремя путями: ручной ввод, импорт CSV из DICAM, API-синк (заглушка).
3. Показывает хронологическую ленту исследований с маркерами «Первое» / «Последнее».
4. Считает попарную дельту любых двух исследований по всем параметрам.
5. Отдаёт выгрузку всех исследований пациента в JSON.
6. Даёт лечащему врачу read-only доступ к исследованиям своих пациентов.

### 1.3 Что модуль НЕ делает (границы)

- Не подключается к аппарату DIERS напрямую — прибора в контуре нет.
- Не разбирает нативные форматы DICAM (проприетарная БД, DICOM, PDF-протоколы).
- Не хранит изображения/3D-модели спины — только числовые параметры.
- Не даёт нормативных диапазонов и клинической интерпретации значений.
- Не строит графиков-трендов (лента — текстовая, сравнение — табличное).
- Не формирует печатный протокол/PDF-отчёт.

## 3. Архитектура

```
┌─────────────────────────┐         ┌──────────────────────────────┐
│  DIERS formetric 4D     │  CSV    │  DICAM Software (клиника)    │
│  DIERS Myoline          ├────────►│  File > Export > CSV         │
└─────────────────────────┘         └──────────────┬───────────────┘
                                                   │ выгрузка файла
                                                   ▼
        ┌──────────────────────────────────────────────────────────┐
        │  Клиент (React + @tanstack/react-query)                  │
        │  ├─ DiersModule.tsx        — пациент (не смонтирован)    │
        │  └─ PatientDiersViewer.tsx — врач, read-only             │
        └───────────────────────┬──────────────────────────────────┘
                                │ REST, Bearer из cookie fitmed_t
                                ▼
        ┌──────────────────────────────────────────────────────────┐
        │  Express                                                 │
        │  ├─ server/routes.ts:5690-5835        — /api/diers/*     │
        │  ├─ server/routes.ts:5824-5915        — /api/myoline/*   │
        │  └─ server/doctor_routes.ts:54-88     — /api/doctor/*    │
        └───────────────────────┬──────────────────────────────────┘
                                │ sqlite.prepare(...) — параметризованный SQL
                                ▼
        ┌──────────────────────────────────────────────────────────┐
        │  PostgreSQL (drizzle)                                    │
        │  ├─ diers_studies    (+ idx user_id, study_date)         │
        │  └─ myoline_studies  (+ idx user_id, study_date)         │
        └──────────────────────────────────────────────────────────┘
```

**Особенность стека:** таблицы объявлены через `pgTable` (Postgres), но обращение
к ним идёт через обёртку `sqlite.prepare(...)` — наследие миграции SQLite → Postgres.
JSON-поля хранятся как `text`, код кладёт `JSON.stringify` и читает `JSON.parse`
(см. комментарий в `shared/schema.ts:1650-1657`). Это осознанное решение авторов
схемы, не дефект, но накладывает ограничения (раздел 8.2).

## 4. Модель данных (сводка)

Полное описание — [Приложение А](./annex-a-data-model.md).

### 4.1 `diers_studies`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | serial PK | |
| `user_id` | integer NOT NULL | владелец-пациент; **FK отсутствует** |
| `study_date` | text | календарная дата, `YYYY-MM-DD` |
| `device_type` | text, def. `formetric4d` | `formetric4d` \| `formetric3d` |
| `title` | text | человекочитаемое название |
| `spine_params` | text (JSON) | параметры позвоночника |
| `posture_params` | text (JSON) | параметры постуры |
| `gait_params` | text (JSON) | параметры походки |
| `raw_data` | text (JSON) | полный CSV-ряд при импорте |
| `source` | text, def. `manual` | `manual` \| `csv_import` |
| `notes` | text | заметки врача/пациента |
| `created_at` | timestamp def. now() | |

Индекс: `diers_studies_user_date_idx (user_id, study_date)`.

### 4.2 Состав параметров

**Позвоночник** (`spine_params`) — 16 распознаваемых ключей:
`VP`, `VP_SD`, `TP`, `TP_SD`, `LP`, `LP_SD`, `KA`, `KA_SD`, `LA`, `LA_SD`,
`Kyphosis`, `Lordosis`, `Scoliosis`, `Trunk_Imbalance`, `Pelvis_Tilt`,
`Sacrum_Inclination`.

**Постура** (`posture_params`) — 7 ключей:
`Trunk_Flex`, `Lat_Dev`, `Rot_Asym`, `Shoulder_Tilt`, `Hip_Tilt`, `COG_X`, `COG_Y`.

**Походка** (`gait_params`) — 6 ключей:
`Step_Length`, `Stride_Width`, `Cadence`, `Speed`, `Stance_Phase`, `Swing_Phase`.

Форма ручного ввода покрывает подмножество: 6 спинальных + 4 постуральных
параметра; походка вручную не вводится вовсе.

> Все значения хранятся **строками** (как пришли из формы/CSV). Числами они
> становятся только в момент сравнения (`parseFloat`). Единицы измерения нигде
> не хранятся — они зашиты в подписи полей UI (°, мм).

### 4.3 `myoline_studies`

`id`, `user_id`, `study_date`, `title`, `emg_channels` (JSON-массив),
`muscle_groups` (JSON-массив), `analysis_results` (JSON), `raw_data`, `source`,
`notes`, `created_at`. Канал ЭМГ: `{ name, raw_value, unit: "µV" }`.
Штатный набор — 12 мышц (6 пар L/R): Erector Spinae, Quadratus Lumborum,
Gluteus Maximus, Rectus Femoris, Tibialis Ant, Gastrocnemius.

## 5. Функциональные требования

### ФТ-1. Ведение исследований `[РЕАЛИЗОВАНО]`

- ФТ-1.1 Список исследований пациента, сортировка по `study_date DESC` на сервере,
  ASC на клиенте для ленты.
- ФТ-1.2 Создание: все параметрические поля опциональны; отсутствующие сохраняются
  как `{}`; `device_type` по умолчанию `formetric4d`; `title` при пустом значении
  генерируется как `Formetric 4D — {дата}`.
- ФТ-1.3 Обновление: `PATCH` с `COALESCE` — передаются только изменяемые поля
  (`title`, `notes`, три группы параметров). Дата и `device_type` не редактируются.
- ФТ-1.4 Удаление: жёсткое (`DELETE`), скоуп `id + user_id`. Мягкого удаления и
  корзины нет.

### ФТ-2. Импорт CSV из DICAM `[РЕАЛИЗОВАНО]`

Полные правила — [Приложение В](./annex-c-csv-mapping.md).

- ФТ-2.1 Приём файла через `multipart/form-data`, поле `file`, доп. поле
  `device_type`. UI ограничивает выбор `.csv, .txt`.
- ФТ-2.2 Разделитель определяется регуляркой `[;,\t]` — поддержаны `;`, `,`, таб
  (европейский экспорт DICAM использует `;`).
- ФТ-2.3 Кавычки `"` вырезаются из заголовков и значений.
- ФТ-2.4 Каждая строка файла → отдельное исследование (батч-импорт истории).
- ФТ-2.5 Дата берётся из первого найденного столбца: `Date` → `Datum` → `date` →
  `study_date`; если не найдена — текущая дата.
- ФТ-2.6 Название: `Title` → `Titel` → `Исследование {N}`.
- ФТ-2.7 Столбцы раскладываются по трём группам по **вхождению подстроки** ключа
  в имя заголовка (`h.includes(k)`) — не точным совпадением. Порядок проверки:
  spine → posture → gait; первое совпадение выигрывает.
- ФТ-2.8 Нераспознанные столбцы в группы не попадают, но целиком сохраняются
  в `raw_data`.
- ФТ-2.9 Ответ: `{ imported: N, studies: [...] }`. Временный файл удаляется
  (`fs.unlinkSync`) при успехе.
- ФТ-2.10 `source = "csv_import"`, в UI помечается бейджем «CSV».

### ФТ-3. Сравнение двух исследований `[РЕАЛИЗОВАНО]`

- ФТ-3.1 Вход: `id1`, `id2` (query). Оба скоупятся по `user_id` вызывающего.
- ФТ-3.2 Объединяется множество ключей обоих исследований — параметр, которого
  нет в одном из них, показывается как `—`.
- ФТ-3.3 `delta = round(v2 - v1, 2)`; если хотя бы одно значение непарсибельно —
  `delta = null`, `direction = "—"`.
- ФТ-3.4 `direction ∈ { "↑", "↓", "=", "—" }`.
- ФТ-3.5 Ответ разбит на три секции: `spine`, `posture`, `gait`; пустые секции
  клиент скрывает.
- ФТ-3.6 Пресет «Первое ↔ Последнее» подставляет крайние по дате исследования.
- ФТ-3.7 Кнопка сравнения заблокирована, пока не выбраны два **разных** исследования.

> **Клиническое замечание.** `direction: "↑"` в UI всегда окрашен в зелёный,
> `"↓"` — в красный (`DiersModule.tsx:40`, `PatientDiersViewer.tsx:27`). Для
> `Scoliosis`, `Trunk_Imbalance`, `Pelvis_Tilt` рост значения — **ухудшение**,
> и зелёный цвет вводит в заблуждение. См. Д-04.

### ФТ-4. Экспорт `[РЕАЛИЗОВАНО]`

- ФТ-4.1 `GET /api/diers/export` — все исследования пациента, ASC по дате,
  `Content-Disposition: attachment`, имя `diers_studies_{userId}_{YYYY-MM-DD}.json`.
- ФТ-4.2 Экспорт отдаёт строки **целиком**, включая `raw_data` — то есть весь
  исходный CSV-ряд. См. Д-06.
- ФТ-4.3 Врач выгружает не через эндпоинт, а собирая Blob из уже загруженного
  ответа `/api/doctor/patient-studies/:id` (`PatientDiersViewer.tsx:63-69`).

### ФТ-5. Интеграция с DICAM `[ЗАГЛУШКА]`

`POST /api/diers/api-sync` — намеренно документированная заглушка. Возвращает
`status: "stub"`, текст-объяснение и три варианта интеграции:

| Метод | Статус | Суть |
|---|---|---|
| CSV Export | `available` | File > Export > CSV в DICAM → `/api/diers/import-csv` |
| HL7 FHIR | `requires_setup` | FHIR-брокер на стороне клиники |
| DICAM Plugin API | `requires_license` | партнёрская лицензия DIERS International |

Плюс `sample_payload` с эталонной структурой параметров. Требует непустой `host`,
иначе `400`. Никакого сетевого обращения не делает.

**Обоснование:** у DIERS formetric нет публичного REST API; реальная интеграция
требует DICAM v4+ с плагином экспорта либо HL7-моста.

### ФТ-6. Врачебный доступ `[ЧАСТИЧНО]`

- ФТ-6.1 `GET /api/doctor/patient-studies/:patientId` — отдаёт `{ diers, myoline }`
  одним запросом, **без** поля `raw_data` (явный список столбцов в SELECT).
- ФТ-6.2 `GET /api/doctor/patient-studies/:patientId/diers-compare` — сравнение,
  скоуп по `patientId`. **Эндпоинт написан, но клиентом не вызывается** (Д-02).
- ФТ-6.3 Врач не может создавать, редактировать и удалять исследования.

## 7. Нефункциональные требования

- **НФТ-1.** Список исследований и сравнение — синхронные запросы, без пагинации.
  Индекс `(user_id, study_date)` покрывает и выборку, и сортировку.
- **НФТ-2.** Импорт CSV синхронный, в одном HTTP-запросе, по одному `INSERT`
  на строку. При файле в тысячи строк это тысячи round-trip'ов в одном запросе.
  Ограничения на размер нет. `[ТРЕБУЕТСЯ]` батч-вставка + лимит.
- **НФТ-3.** Интерфейс — тёмная тема, мобильный формат (компактные размеры
  шрифтов 9–12px, `rounded-xl`), палитра: cyan — DIERS, violet — Myoline.
- **НФТ-4.** Локализация: интерфейс русский, **значения параметров — английские
  технические ключи** (`Kyphosis`, `COG_X`, `VP/TP/LP`). Словаря нет. Д-03.
- **НФТ-5.** Доступность: карточки исследований — кликабельные `div` без `role`,
  `tabIndex` и клавиатурной активации. Д-07.
- **НФТ-6.** Тесты: автотестов на модуль **нет** ни на бэкенде, ни на клиенте
  (проверено по `tests/`). Д-08.
- **НФТ-7.** `DiersModule.tsx` числится в списке файлов с предсуществующими
  ошибками `tsc --noEmit` (`docs/PRODUCT-AUDIT-by-window.md:192`).

## 8. Ограничения и осознанные компромиссы

### 8.1 Интеграционные

Прибор в контур не заведён и, вероятнее всего, заведён не будет без партнёрской
лицензии DIERS International. Рабочий путь один: ручная выгрузка CSV из DICAM →
загрузка в систему. Любые ожидания «автоматической синхронизации с аппаратом»
на текущей архитектуре несостоятельны.

### 8.2 Схемные

JSON в `text`-полях исключает индексацию и запросы по отдельному параметру
(«найди всех, у кого Scoliosis > 10°»). Сравнение и агрегация считаются
в приложении. Пока задача — «показать динамику одного пациента», это приемлемо;
для когортной аналитики потребуется `jsonb` или вынос параметров в отдельную
таблицу «параметр–значение».

### 8.3 Клинические

Модуль — хранилище и «калькулятор дельты», не система поддержки принятия решений.
Нет референсных диапазонов, нет учёта пола/возраста, нет порогов клинической
значимости изменения. Знак дельты не равен клиническому улучшению.

## 9. Требования к целевой версии

Полный реестр с приоритетами — [Приложение Г](./annex-d-defects-backlog.md).
Сжато, по приоритетам:

**P0 — блокирует использование**
1. Смонтировать `DiersModule` в интерфейс пациента (Д-01).
2. Починить сравнение у врача: переключить на `/api/doctor/patient-studies/:id/diers-compare` (Д-02).

**P1 — корректность и безопасность**
3. Валидация и лимиты импорта CSV: размер файла, число строк, MIME (Д-05).
4. Убрать fallback, кладущий весь CSV-ряд в `spine_params` при нераспознанных заголовках (Д-09).
5. Клинически корректная окраска дельты — по семантике параметра, не по знаку (Д-04).
6. Исключить `raw_data` из пациентского экспорта либо сделать опцией (Д-06).

**P2 — качество**
7. Словарь локализации параметров DIERS на русский (Д-03).
8. Доступность карточек: `button`/`role`/клавиатура (Д-07).
9. Автотесты: импорт CSV, скоупинг по пользователю, дельта-расчёт (Д-08).
10. График-тренд по выбранному параметру вместо только табличной дельты.
11. Референсные диапазоны и подсветка выхода за норму.
12. Печатный протокол «до/после» (PDF) — уже востребован сценарием челленджа
    «Здоровая спина» (`server/challenge_routes.ts:124`).
