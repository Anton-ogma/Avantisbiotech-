# Приложение Г. Реестр дефектов и бэклог

Источник: код `fitmed-ecosystem@3a028f0`; часть пунктов подтверждается
внутренним аудитом `docs/PRODUCT-AUDIT-by-window.md:1008-1027`.

Приоритеты: **P0** — блокирует использование, **P1** — корректность/безопасность,
**P2** — качество и удобство.

---

## Г.1 Реестр дефектов

### Д-01 · P0 · Модуль пациента не подключён к интерфейсу

`client/src/components/DiersModule.tsx` (884 строки) не импортируется ни одной
страницей. Проверено grep по `client/`, `frontend/`, `server/`: единственные
вхождения `DiersModule` — само определение компонента и упоминание в
`frontend/MIGRATION_GUIDE.md` как «ещё не мигрированного».

**Следствие:** пациент не может ни добавить исследование, ни импортировать CSV,
ни посмотреть свою динамику. Весь пациентский путь (П-1…П-8) недоступен.
Данные в системе могут появиться только если их создать напрямую через API.

**Исправление:** смонтировать модуль в соответствующий раздел приложения
пациента (по аналогии с `PatientDiersViewer` в `DoctorDashboard.tsx:427`).

---

### Д-02 · P0 · Сравнение у врача всегда возвращает 404

`PatientDiersViewer.tsx:56` вызывает **пациентский** `/api/diers/compare`,
который скоупит выборку по `user_id` **врача**. Исследования принадлежат
пациенту → обе записи не находятся → `404` → тост «Нет доступа к данному пациенту».

Правильный эндпоинт `/api/doctor/patient-studies/:patientId/diers-compare`
(`doctor_routes.ts:69`) реализован, но не вызывается.

Рядом — мёртвая строка `PatientDiersViewer.tsx:55`:

```js
const patientId = studies[0]?.id ? null : null; // всегда null
```

**Исправление:** пробросить `patientId` из пропсов в `DoctorDiersPanel`,
вызвать doctor-эндпоинт, удалить строку 55.

---

### Д-03 · P2 · Параметры показываются английскими техническими ключами

Русскоязычный врач видит `Kyphosis`, `Lordosis`, `Scoliosis`, `Trunk_Imbalance`,
`Sacrum_Inclination`, `COG_X`, `VP/TP/LP` — как в карточке, так и в таблице
сравнения (`PatientDiersViewer.tsx:195, 259-262`; `DiersModule.tsx:251, 500`).
Русские подписи существуют **только** в форме ручного ввода (`DiersModule.tsx:188-190,
203-204`) и нигде больше не переиспользуются.

**Исправление:** справочник параметров (`code → {label_ru, unit, …}`), общий для
формы, карточки и сравнения.

---

### Д-04 · P1 · Окраска дельты не соответствует клиническому смыслу

`DiersModule.tsx:40`, `PatientDiersViewer.tsx:27`:

```js
const color = dir === "↑" ? "text-emerald-400" : dir === "↓" ? "text-red-400" : …
```

Рост значения всегда зелёный, снижение — красный. Для `Scoliosis`,
`Trunk_Imbalance`, `Pelvis_Tilt`, `Lat_Dev` рост — **ухудшение**. Врач и пациент
видят зелёный там, где состояние ухудшилось.

**Исправление:** признак «направление улучшения» в справочнике параметров
(Д-03); для параметров без клинически однозначного направления — нейтральный цвет.

---

### Д-05 · P1 · Импорт CSV без валидации и лимитов

`/api/diers/import-csv` и `/api/myoline/import-csv`: файл читается целиком в
память, число строк не ограничено, MIME не проверяется, на каждую строку —
отдельный `INSERT`. Ограничение `.csv,.txt` действует только в атрибуте `accept`
файлового инпута, то есть обходится любым прямым запросом.

**Исправление:** лимит размера в `uploadMiddleware`, лимит числа строк,
проверка MIME/расширения на сервере, батч-вставка.

---

### Д-06 · P1 · Пациентский экспорт отдаёт `raw_data`

`GET /api/diers/export` возвращает строки целиком, включая `raw_data` — полный
исходный CSV-ряд, где могут быть ФИО, идентификатор пациента в DICAM и прочие
поля клиники. Врачебный эндпоинт `raw_data` корректно исключает — здесь
исключения нет.

**Исправление:** явный список столбцов в SELECT либо параметр `?include_raw=1`.

---

### Д-07 · P2 · Недоступность карточек с клавиатуры

Карточки исследований — кликабельные `<div onClick>` без `role="button"`,
`tabIndex`, обработки Enter/Space (`DiersModule.tsx:483`, `PatientDiersViewer.tsx:244`).
Статусы «Первое»/«Последнее» кодируются цветом точки на таймлайне —
цвет как единственный носитель смысла.

**Исправление:** `<button>` либо `role` + `tabIndex` + клавиатурные обработчики.

---

### Д-08 · P2 · Нет автотестов

В `tests/` нет ни одного файла, упоминающего DIERS или Myoline.

**Минимальный набор:** разбор CSV (разделители, кавычки, пропуски, нераспознанные
столбцы), скоупинг выборок по `user_id`, расчёт дельты (в т.ч. нечисловые
значения и односторонние ключи), проверки ролей и связи врач–пациент.

---

### Д-09 · P1 · Фолбэк импорта пишет весь CSV-ряд в `spine_params`

`routes.ts:5759`:

```js
JSON.stringify(Object.keys(spine_params).length ? spine_params : row)
```

Если ни один заголовок не распознан как спинальный, в `spine_params` уходит
**вся строка файла**. Раздел «Позвоночник» заполняется произвольными столбцами,
сравнение выдаёт мусор, содержимое дублирует `raw_data`.

**Исправление:** сохранять `{}` и возвращать отчёт о нераспознанных столбцах.

---

### Д-10 · P2 · `PATCH` отдаёт запись без скоупа по пользователю

`routes.ts:5718`: после `UPDATE … WHERE id=? AND user_id=?` идёт
`SELECT * FROM diers_studies WHERE id=?` — **без** `user_id`. При обращении
к чужому `id` обновления не произойдёт, но чужая запись вернётся в ответе.

**Исправление:** добавить `AND user_id=?` в SELECT.

---

### Д-11 · P2 · Временный файл не удаляется при ошибке импорта

`fs.unlinkSync(req.file.path)` вызывается только на успешном пути; исключение
в цикле оставляет файл на диске.

**Исправление:** удаление в `finally`.

---

### Д-12 · P2 · Отсутствующий канал ЭМГ трактуется как нулевая активность

`/api/myoline/compare`: `parseFloat(c1?.raw_value || '0')`. Если канал есть
только в одном исследовании, второй считается нулём — дельта получается
максимальной и выглядит как обвал или всплеск активности мышцы, которую просто
не измеряли. В `v1`/`v2` при этом честно стоит `"—"`.

**Исправление:** `delta: null`, `direction: "—"` при отсутствии канала —
как это сделано в DIERS-сравнении.

---

### Д-13 · P1 · `diers-compare` у врача не проверяет связь с пациентом

`doctor_routes.ts:69-88` проверяет роль (`doctor`/`admin`), но, в отличие от
соседнего `/patient-studies/:patientId`, **не проверяет** наличие брони пациента
у этого врача. Любой пользователь с ролью `doctor`, зная `patientId` и пару `id`,
получит значения параметров чужого пациента.

Сейчас риск не реализуется только потому, что клиент этот эндпоинт не вызывает
(Д-02). При исправлении Д-02 дыра станет доступной — **чинить в одном изменении**.

**Исправление:** перенести проверку `isPatient` из `/patient-studies/:patientId`
в общий middleware для обоих doctor-эндпоинтов.

---

### Д-14 · P2 · Токен в cookie, читаемой из JavaScript

Клиент повсеместно достаёт токен через `document.cookie` и шлёт `Bearer`
(`DiersModule.tsx:102, 112, 123`; `PatientDiersViewer.tsx:53, 399`). Значит,
cookie `fitmed_t` не может быть `httpOnly` и доступна при XSS. Это архитектурное
решение всей системы, не только модуля DIERS, — фиксируется как контекст.

---

### Д-15 · P2 · Ошибки `tsc` в `DiersModule.tsx`

Файл числится в списке предсуществующего техдолга по типам
(`docs/PRODUCT-AUDIT-by-window.md:192`). Перед монтированием (Д-01) типы
следует привести в порядок.

## Г.3 Рекомендуемый порядок работ

**Итерация 1 — сделать модуль работающим**
Д-01 (смонтировать) → Д-15 (типы) → Д-02 + Д-13 одним изменением
(починить сравнение у врача и одновременно закрыть проверку связи с пациентом).

**Итерация 2 — корректность данных**
Д-09 (фолбэк импорта) → Д-05 (лимиты и валидация) → Д-06 (`raw_data` в экспорте)
→ Д-10, Д-11, Д-12 → Ф-7 (дедупликация).

**Итерация 3 — клиническая пригодность**
Справочник параметров как единая основа: Д-03 (русские подписи),
Д-04 (семантика направления), Ф-2 (нормы). Затем Ф-1 (тренд) и Ф-3 (PDF).

**Сквозное:** Д-08 (тесты) — писать вместе с каждым исправлением, а не отдельной
итерацией.
