# ТЗ на реализацию: постуральный модуль DIERS

Версия 1.0 · документ для разработки. Заменяет ранние черновики в части реализации;
методические обоснования остаются в отдельных документах и здесь не повторяются.

## 0. Как читать этот документ

- **MUST** — обязательно, без этого приёмка не проходит.
- **SHOULD** — сильная рекомендация, отклонение фиксируется в решении.
- **MAY** — на усмотрение команды.
- Разделы 4–12 — контракт данных и алгоритмов, менять только через ревью.
- Все числовые пороги и нормы в примерах — **демонстрационные**. Продуктовые значения
  приходят из конфигурации (§10) и в код не зашиваются никогда.

## 1. Границы системы

Система — **научно-практическая платформа**: она предназначена выявлять закономерности,
а не применять готовые. Комбинация оборудования и целей прецедента не имеет, протоколы
разрабатываются здесь же. Нормы, пороги, направление «лучше/хуже» и правила —
параметры исследования, а не константы; каждое поддерживает состояние «не определено»
и своим отсутствием работу платформы не блокирует.

MUST (Р-19): развёртывание имеет явный режим назначения `intended_use ∈ {research, clinical}`.
В режиме `research` движок правил (§11) отключён — платформа выдаёт наблюдения и
статистику, но не терапевтические назначения. В режиме `clinical` правило загружается,
только если опирается на параметры с установленным направлением и на закономерности,
прошедшие подтверждающий анализ.

Требования к дизайну исследования — предрегистрация, слепая оценка качества,
sham-условие, контроль множественности, lockbox — вынесены в
[исследовательский контур](./research-framework.md) и обязательны наравне с настоящим
документом.

В клиническом применении система остаётся **инструментом поддержки решений врача**.
Она не ставит диагноз и не назначает лечение автономно.

MUST:
- любой вывод (отклонения, ранжирование проб, рекомендации, прогноз) создаётся в статусе `draft`;
- переход в `signed` возможен только действием пользователя с ролью «врач»;
- отчёт в статусе `draft` не выгружается пациенту и не печатается без водяного знака;
- в каждом отчёте печатаются версии норм, порогов и правил.

Регуляторный контекст: софт, предлагающий терапевтические действия, с высокой вероятностью
попадает под MDR. Это влияет на требования §15 (аудит, версионирование, воспроизводимость) —
их нельзя откладывать «на потом».

Вне рамок первой версии: биофидбек в реальном времени, интеграция с ЭМР клиники, мобильное
приложение пациента, автоматическое проектирование стелек.

## 2. Глоссарий и коды

| Термин | Значение |
|---|---|
| Проба (probe) | стандартизованное условие обследования: положение НЧ, аппарат, клин |
| Нейтраль | опорная проба, относительно которой считаются все Δ |
| Sham | методически неактивное условие, неотличимое для пациента от активного |
| PI | постуральный индекс, сводная удалённость от нормы; требует норм |
| RI | индекс отзывчивости, сводная величина отклика в единицах SDC; норм не требует |
| SDC | наименьшее выявляемое изменение параметра |
| Effect size | Δ / SDC |
| Домен | группа параметров: `frontal`, `pelvis`, `rotation`, `sagittal`, `support`, `leg_axis` |
| Когерентность | согласованность изменения по позе, суставу и мышце |

Коды проб (справочник, расширяем через конфигурацию):

```
MAND_NEUTRAL_NO_APPARATUS   MAND_NEUTRAL_WITH_APPARATUS
MAND_CLENCH  MAND_PROTRUSION  MAND_RETRUSION
MAND_LAT_LEFT  MAND_LAT_RIGHT  MAND_OPEN
MAND_SPLINT_JOINT  MAND_SPLINT_THERAPEUTIC  MAND_COTTON_ROLLS
PODAL_WEDGE_L  PODAL_WEDGE_R  PODAL_HEEL_LIFT  PODAL_INSOLE_PROTO  PODAL_BAREFOOT_REF
CTRL_TASK_NONORAL  CTRL_TONGUE  CTRL_SHAM_<уровень>
COMBI_<A>_PLUS_<B>
```

`CTRL_SHAM_*` добавлен решением Р-15: без sham изменение позы под пробой объясняется
временем, вниманием и ожиданием эффекта. Повторная нейтраль контролирует дрейф,
но не сам факт вмешательства.

## 3. Стек и структура

MUST:
- бэкенд Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic;
- БД PostgreSQL 16;
- очередь Redis + ARQ;
- объектное хранилище S3-совместимое (MinIO on-prem);
- фронтенд React + TypeScript, сборка Vite;
- типы фронтенда генерируются из Pydantic-моделей, ручное дублирование запрещено;
- Bridge Agent — Python + watchdog, сборка PyInstaller, служба Windows.

Если хост-приложение написано на другом языке, весь домен выносится отдельным Python-сервисом
с контрактом §13; смешивать домен между языками запрещено.

Р-10: хост — `fitmed-ecosystem` (TypeScript/Express), поэтому действует именно этот вариант.
Модуль реализуется отдельным Python-сервисом со своей БД и разворачивается самостоятельно;
хост обращается к нему только по §13. Существующий TS-модуль DIERS в fitmed целевым
не становится и в кодовую базу модуля не переносится.

```
apps/  web · api · worker-signal · worker-report · bridge-agent
packages/
  domain/      canonical · protocol · analysis · rules · report   ← чистые функции
  importers/   formetric · pedoscan · myoline · emg · condylography
  contracts/   Pydantic + генерация TS
  config/      norms · thresholds · probes · rules   (YAML, версионируется)
analytics/     Python-ноутбуки, НЕ связаны с рантаймом
db/migrations/
tests/         fixtures · golden
```

MUST: `packages/domain` не обращается к БД, сети и системным часам. Всё приходит аргументами.

и входят в контракт наравне с перечисленными.

Инварианты (MUST, проверяются тестами):
1. `raw_imports.file_hash` уникален — повторная загрузка не создаёт второе обследование.
2. `analyses.input_hash = sha256(канонические данные + пять версий конфигурации:
   norms, thresholds, rules, profile, registry)`; одинаковый вход даёт побайтово
   одинаковый `result` (Р-3).
3. Версии конфигурации в `analyses` и `sessions` — **копии значений**, не ссылки на «текущее».
4. `audit_log` — только вставка; UPDATE и DELETE запрещены правами БД.
5. `analyses` — только вставка; переанализ порождает новую строку, прежние сохраняются.
   Подписанный отчёт остаётся привязан к своей строке `analyses` навсегда (Р-2).
6. `sessions.neutral_definition` — копия значения `patients_ref` на момент создания
   сессии; последующая смена у пациента прошлые сессии не переписывает (Р-8).

## 5. Импорт

### 5.1 Источники

MUST поддерживаться два пути, оба приводящие в один канонический слой:

- **Агент**: Bridge Agent следит за настроенными папками на приборных ПК, считает хэш,
  ставит файл в очередь, переживает отсутствие сети (локальная очередь с повтором).
- **Ручная загрузка**: форма в веб-интерфейсе, те же форматы, та же очередь.

Каждый импорт хранит `source` (agent|manual). Молчаливый пропуск файла запрещён:
нераспознанный формат остаётся в очереди со статусом `unrecognized` и причиной.

### 5.2 Парсеры

Контракт:

```python
class Parser(Protocol):
    format_id: str            # 'formetric-xml-v4'
    modality: str
    def detect(self, blob: bytes) -> bool: ...
    def parse(self, blob: bytes) -> CanonicalMeasurement | RawSeries: ...
```

MUST:
- один парсер на версию формата, выбор через `detect`;
- фактическая частота дискретизации берётся из заголовка файла и сравнивается с заявленной;
  расхождение — флаг `resample_suspected`;
- десятичный разделитель определяется по содержимому файла, не по локали сервера;
- на каждый парсер в `tests/fixtures` лежит реальный файл и ожидаемый разбор.

Поддерживаемые форматы первой версии: formetric XML и CSV, pedoscan CSV, ЭМГ C3D / EDF / CSV
вендора, аксиография XML, плюс форма ручного ввода сводных показателей аксиографии.

### 5.3 Знаки и единицы

MUST: модуль `canonical/sign_conventions` — единственное место, где задаются знаковые соглашения
и единицы по версиям формата. Property-тест: зеркальный набор входных данных даёт зеркальный
результат по всем знаковым параметрам. Этот тест пишется до первого парсера.

## 6. Синхронизация

Три уровня, реализуются независимо:

| Уровень | Точность | Механизм | Обязательность |
|---|---|---|---|
| E — эпохи | ±150 мс | программные маркеры, общие часы | MUST |
| M — семантический | нет времени | сопоставление по коду пробы | MUST |
| S — сэмплы | ±5 мс | аппаратный триггер / общий аналоговый канал | MAY, этап 4 |

### 6.1 Уровень E (ЭМГ, pedoscan)

- одна непрерывная запись на сессию, эпохи нарезаются по маркерам;
- модель времени канала `t_common = a·t_sensor + b`;
- `a` и `b` оцениваются по **двум** синхрособытиям — в начале и в конце сессии;
  одно событие недопустимо;
- детектор разрывов по счётчику сэмплов; интерполяция только для разрывов < 20 мс;
  эпоха с превышением получает флаг `dropout` и исключается из анализа.

### 6.2 Уровень M (кондилография)

- сопоставление по `probe_code`;
- MUST: сверка `excursion_mm` записи аксиографии и формометрической пробы,
  допуск задаётся конфигурацией (по умолчанию ±1,0 мм);
  при превышении `match_status = mismatch`, связка не строится, флаг выводится в отчёт;
- контрольные пробы `MAND_NEUTRAL_WITH_APPARATUS` и `MAND_NEUTRAL_NO_APPARATUS` обязательны,
  все кондилографические Δ считаются от нейтрали **с аппаратом**.

## 7. Канонизация

`param_registry` — реестр параметров: код, модальность, единица, домен, направление
(`two_sided` | `higher_worse` | `lower_worse` | `unknown`), участие в PI.

MUST (Р-18): `unknown` — штатное значение для параметра, по которому закономерность ещё
не установлена, и значение **по умолчанию** для нового параметра. Такой параметр входит
в `RI` по модулю, показывается нейтральным цветом без слов «улучшение»/«ухудшение»,
в правила рекомендаций не входит. Смена `unknown` на определённое направление — это
изменение `registry_version` и требует ссылки на подтверждающий анализ, который
направление установил. Так результат исследования попадает в продукт.

MUST: реестр версионируется (`registry_version`), входит в `input_hash` и в проверку
сопоставимости §12 — изменение домена, направления или участия параметра в PI меняет
результат при тех же измерениях (Р-3). Реестр проб (§10) версионируется отдельно,
через уже существующее `sessions.protocol_version`, и в `input_hash` не входит:
на арифметику анализа он не влияет.

Обязательный минимум формометрии: дисбаланс туловища VP-DM, сагиттальный дисбаланс,
боковое отклонение rms и max, ротация позвонков rms и max, поверхностная ротация rms,
угол кифоза ICT-ITL, угол лордоза ITL-ILS, перекос таза DL-DR, торсия таза, ротация таза,
наклон таза, наклон туловища. Полный список 40 параметров подключается по мере появления
реального экспорта.

Pedoscan: доли нагрузки лево/право, передний/задний отдел по сторонам, длина пути ЦД,
площадь ЦД, площадь контакта, индекс свода, матрица давления.

Флаги качества: `missing_landmark`, `cropped_frame`, `excess_sway`, `foot_shift`,
`resample_suspected`, `low_snr`, `clipping`, `dropout`, `line_noise_high`,
`ecg_contamination`, `motion_artifact`, `sync_uncertain`.

## 8. Протокол сессии

### 8.1 Машина состояний

```
prepared → baseline_recorded → probes_running → imported → quality_reviewed → shortlist_confirmed → analyzed → reported
```

Это единственное состояние сессии, хранится в `sessions.status` (решение Р-1).
Переходы односторонние, каждый пишется в `audit_log`. Признак `low_confidence` (§8.2)
ортогонален состоянию и хранится отдельным полем, значением статуса не является.
Статусы отчёта (`draft`/`signed`, §1) живут в `reports.status` и с состоянием сессии
не пересекаются.

Валидаторы (MUST, блокируют переход):

1. `neutral_definition` задан у пациента и не меняется внутри курса; смена требует явного
   действия и снимает сопоставимость с прошлыми визитами.
2. Порядок групп: `reference → diagnostic → podal → therapeutic`. Рандомизация допустима
   только внутри группы. Терапевтическая проба до диагностических не допускается.
3. Выдержка: фактическое `settle_sec` ≥ заданного в реестре проб.
4. Washout между группами ≥ `carryover_min`.
5. Проверка контакта электродов пройдена до начала записи.
6. Для эксцентрических проб заполнен `excursion_mm`; для сжатия — `effort.achieved_pct`.
7. Разница длины ног измерена и компенсация зафиксирована **до** челюстных проб.
8. Нейтраль записана минимум трижды: начало, середина, конец.
9. (Р-15) В сессии со `study_mode = true`, содержащей терапевтическую пробу, присутствует
   sham соответствующего уровня.
10. (Р-16) При `randomization_scheme ≠ none` зафиксирован `randomization_seed`.
11. (Р-17) Решения шага `quality_reviewed` приняты вслепую: код пробы, роль, порядковый
    номер и результаты анализа на экране разбора скрыты до фиксации всех решений.

### 8.2 Дрейф и валидность

`baseline_drift = |PI(нейтраль_последняя) − PI(нейтраль_первая)|`.
Если превышает `thresholds.PI`, сессия помечается `low_confidence`, и это печатается в отчёте.

`baseline_ref` = среднее значений нейтрали с линейной поправкой на позицию пробы во времени.

### 8.3 Подтверждающий повтор

Формируются два раздельных списка (Р-5):

- **`shortlist`** — кандидаты в терапию. Только пробы с достоверным **улучшением**
  (`ΔPI < −thresholds.PI`), ранжируются по величине улучшения. После полного прохода
  топ-2 из них измеряются повторно, вперемешку с нейтралью. Проба остаётся в шорт-листе,
  только если повтор подтверждает знак и величина не выходит за порог.
  Неподтверждённые пробы в рекомендации не идут.
- **`notable_worsening`** — пробы с достоверным **ухудшением** (`ΔPI > +thresholds.PI`).
  Диагностически значимы и печатаются в отчёте, включая режим тренера (§14.5, блок
  конфликтов), но в рекомендации не попадают никогда и подтверждающим повтором
  не проверяются — помечаются `unconfirmed`.

Пробы внутри полосы шума не попадают ни в один список (§9.3).

## 9. Алгоритмы анализа

Все функции — чистые, без I/O. Сигнатура верхнего уровня:

```python
def analyze(session: SessionData, norms: NormsTable, thresholds: ThresholdTable) -> AnalysisResult
```

### 9.1 Отклонение от нормы

```
z = (value − norms[code].mean) / norms[code].sd
```
Категории: `|z| < 1` норма, `1 ≤ |z| < 2` пограничное, `2 ≤ |z| < 3` отклонение,
`|z| ≥ 3` выраженное. Границы задаются конфигурацией.

Для тазовых параметров используется **остаточное** значение после компенсации длины ног.

### 9.2 Индексы: PI и RI

```
PI_domain = Σ_p w_p · min(|z_p|, z_cap)          # z_cap по умолчанию 4
PI        = Σ_domain W_domain · PI_domain

RI_domain = Σ_p w_p · min(|Δ_p| / SDC_p, cap)    # отклик, нормированный на порог
RI        = Σ_domain W_domain · RI_domain
```

MUST: `leg_axis` в PI и RI не входит (структурный домен). `W_domain` — из конфигурации
профиля клиники.

MUST (Р-13): `PI` требует норм и вычисляется только для параметров, у которых нормы
определены; `RI` опирается на собственную нейтраль пациента и норм не требует.
**Отсутствие норм не блокирует ни один сценарий.** Параметр без норм участвует в `RI`
и не участвует в `PI`; колонка нормы для него — прочерк (§14.2.5), а не ноль.
В отчёте и на графиках всегда указано, какой индекс использован.

`RI` — основной индекс исследовательского контура: метод по построению измеряет отклик
на пробу, а не удалённость от популяции, поэтому популяционная норма не должна быть
входом для оценки отклика.

### 9.3 Эффект пробы

```
Δ_p            = value(trial)_p − baseline_ref_p
effect_size_p  = Δ_p / SDC_p
ΔPI            = PI(trial) − PI(baseline_ref)
```

Классификация: `|effect| < 1` шум (не интерпретируется), `1 ≤ |effect| < 2` вероятный,
`≥ 2` достоверный. Для ΔPI используется `thresholds.PI`.

MUST: значения ниже порога не участвуют в ранжировании, не попадают в шорт-лист,
не порождают рекомендаций и отображаются нейтральным цветом.

MUST (Р-14): правило выше относится к **клиническому выводу об этом пациенте**.
Подпороговые значения хранятся полностью и участвуют в исследовательском анализе на
уровне когорты. SDC — порог различимости однократного измерения у одного пациента;
ошибка групповой оценки меньше индивидуальной в √n раз, поэтому систематический сдвиг,
неразличимый в отдельном обследовании, обнаруживается на серии. Отбрасывать
подпороговые значения на входе запрещено: именно в этой зоне лежат закономерности,
ранее отвергавшиеся как «в пределах погрешности».

### 9.4 Оси нижней челюсти

```
lateral_mandible:  (MAND_LAT_LEFT, MAND_LAT_RIGHT)
sagittal_mandible: (MAND_PROTRUSION, MAND_RETRUSION)
occlusal_load:     (MAND_CLENCH, MAND_OPEN)
```

Интерпретация оси: `asymmetric_<side>_preference`, если один член пары достоверно улучшает,
а второй нейтрален или ухудшает; `symmetric_worsening`; `no_effect`, если оба в шуме.

### 9.5 Согласованность

Для каждой пробы три знака: поза (`ΔPI`), сустав (симметризация координат мыщелков),
мышца (`ΔMI`). Значения:

| coherence | условие |
|---|---|
| `full` | три домена сходятся, поза достоверна |
| `partial` | два из трёх |
| `posture_only` | поза достоверна, остальные в шуме |
| `posture_muscle_conflict` | поза улучшается, мышечная активность растёт выше порога |

MUST: `ΔMI` считается отдельным индексом и **не суммируется** в PI.

Значение переименовано из `conflict` (Р-6): слово занято вердиктом комбинированной
пробы §9.7, а в отчёте оба поля стоят рядом.

### 9.6 Карта отклика

Точки: координаты мыщелков пробы × ΔPI. MUST: интерполяция только между измеренными
соседними точками, экстраполяция запрещена и визуально штрихуется, точки в шуме
исключаются из поиска оптимума. Аппроксимация поверхностью запрещена.

Ограничения этого раздела относятся к **клиническому отображению**. В исследовательском
контуре моделирование поверхности отклика допустимо и ожидаемо, но его результат —
гипотеза (`exploratory`), которая на клинические экраны не попадает и назначением
не становится (Р-14).

### 9.7 Комбинированная проба

```
add   = ΔPI(A) + ΔPI(B)
best  = min(ΔPI(A), ΔPI(B))          # ΔPI < 0 — улучшение, поэтому лучший = минимальный

verdict — первое совпавшее условие в этом порядке (Р-4):
  conflict      если ΔPI(AB) > best + thresholds.PI      # хуже лучшего одиночного
  synergistic   если ΔPI(AB) < add  − thresholds.PI      # лучше суммы одиночных
  dominant      если |ΔPI(AB) − best| < thresholds.PI    # работает один уровень
  additive      если |ΔPI(AB) − add|  < thresholds.PI    # вклады складываются
  indeterminate иначе
```

MUST: порядок проверки нормативен — условия пересекаются, первое совпадение выигрывает.
`conflict` проверяется первым: комбинация, которая хуже лучшего одиночного уровня, остаётся
конфликтом, даже если численно совпала с суммой. `dominant` проверяется раньше `additive`:
когда вклад одного уровня в пределах шума, клинически честная формулировка — «работает
один уровень», а не «вклады сложились».

MUST: при `conflict` движок правил не выдаёт одновременное назначение обоих уровней.
При `indeterminate` комбинация не интерпретируется и в рекомендации не идёт — требуется
повтор пробы.

### 9.8 ЭМГ

Обработка: удаление постоянной составляющей, полосовой фильтр 20–450 Гц, подавление сети
50 Гц спектральной интерполяцией, контроль ЭКГ-наводки, выпрямление, RMS-огибающая
с окном 100–250 мс.

Метрики: `RMS_MEAN`, `ASYM_LR`, `COCONTRACTION`, `MDF`, `ONSET_LATENCY` (только уровень S).

MUST: сравнение амплитуд в мкВ допускается **только внутри одной сессии** (электроды
не переклеивались). Межсессионное сравнение — только нормализованных величин; при отсутствии
нормализации блок межсессионной динамики ЭМГ не отображается вовсе.

MUST: перед интерпретацией эпохи считается SNR; при значении ниже порога канал помечается
`low_snr` и не интерпретируется.

MUST: myoline (изометрическая сила) не участвует в анализе проб; используется только для
дозирования программы.

Р-12: термин закрепляется за изометрической силой; ЭМГ — отдельная модальность с
собственными таблицами (§4). Данные унаследованной таблицы `myoline_studies` в
`fitmed-ecosystem` хранят амплитуды в мкВ, то есть по существу являются ЭМГ и при
любой миграции трактуются как ЭМГ, а не как myoline.

## 11. Рекомендации

Настоящий раздел действует только при `intended_use = clinical` (§1, Р-19). В режиме
`research` движок правил отключён: платформа выдаёт наблюдения, отклики и статистику,
но не терапевтические назначения.

MUST (Р-19): правило, опирающееся на параметр с `direction = unknown` либо на
неподтверждённую закономерность, не загружается — валидация конфигурации при старте
отклоняет такой файл. Правило нельзя написать раньше, чем закономерность подтверждена,
и это обеспечивается технически, а не регламентом.

MUST: решение принимает движок правил. LLM применяется только для формулировки текста
на основе уже принятого решения; при недоступности сервиса отчёт выпускается с шаблонными
формулировками. Обратный порядок запрещён.

Каждая рекомендация содержит `rule_id`, `version`, перечень сработавших условий.

Логика стелек:

1. структурная разница длины ног → компенсация обязательна, величина из платформы;
2. подальная проба достоверно улучшает остаточные параметры → корригирующий элемент;
   не улучшает → стельки не показаны, даже при «неидеальной» стопе;
3. пересечение с челюстным уровнем → требуется комбинированная проба;
   при `conflict` или отсутствии пробы рекомендация становится последовательной.

Ось ноги за пределами конфигурируемого коридора → флаг `requires_orthopedic_review`;
конструкция модулем не назначается.

Прогноз выдаётся интервалом с условиями, помечается источником (`literature` | `own_cohort`)
и не выдаётся по параметрам, чьё исходное отклонение в пределах SDC.

## 12. История и сопоставимость визитов

MUST: два обследования сопоставимы, только если совпадают
`neutral_definition`, `norms_version`, `thresholds_version`, `profile_version`,
`registry_version`, тип опорной позиции кондилографии и тип аппарата.

`rules_version` в проверку **не входит** (Р-3): правила влияют на рекомендации,
а не на измеренные величины, и их обновление сопоставимость визитов не разрывает.

MUST: сверка идёт по строкам `analyses`, а не по `sessions` (Р-2). Версии в `sessions` —
то, что действовало в момент обследования; версии в `analyses` — то, с чем фактически
посчитали. Переанализ старых сессий под общий набор версий (§13) — штатный способ
восстановить сопоставимость после обновления норм или порогов.

`GET /patients/{ref}/history` по умолчанию подбирает **самый свежий набор версий,
доступный для всех сессий пациента**, и на нём строит динамику; набор можно задать явно
параметрами запроса. Выбранный набор печатается рядом с графиком.

При несовпадении визиты показываются рядом, но разности **не вычисляются**; интерфейс
выводит причину и предлагает переанализ, если сырые данные позволяют. Это правило
распространяется на все межвизитные величины.

Раздельно отслеживаются и никогда не смешиваются:
- `PI(нейтраль)` по визитам — динамика исходного состояния;
- `ΔPI(лучшая проба)` по визитам — динамика отзывчивости.

Порядки отображения: хронологический, по величине отклика, в порядке выбора пользователем.

## 14. Интерфейс

### 14.1 Разделы

`Обзор · Сессия · Импорт · История · Анализ · Пробы · Сравнение · Нижний контур ·
Рекомендации · Отчёт · Методика · Исследование`, плюс отдельный режим «Отчёт тренеру».

### 14.2 Сквозные правила отображения (MUST)

1. **Зона шума рисуется, а не описывается.** В каждом графике сравнения присутствует
   полоса ±SDC; значения внутри неё отображаются нейтральным цветом и без акцента.
2. **Единая шкала.** Все панели одного типа используют одинаковый масштаб; автомасштаб
   на панель запрещён.
3. **Контракт цвета.** Один объект на графике — цвет кодирует направление
   (улучшение/ухудшение/шум). Несколько наложенных — цвет кодирует пробу, направление
   уходит в подпись.
4. **Нейтраль не снимается** ни в одном сравнении.
5. **Норма показывается только там, где определена.** Для координат мыщелков и амплитуд ЭМГ
   колонка нормы — прочерк.
6. **Прочерк и дефект различаются.** «Данных не предполагается» и «данные ожидались, но
   непригодны» — разные состояния с разным оформлением.
7. **Поля не накладываются.** Отпечатки стоп и матрицы давления сравниваются парно плюс
   карта разности с порогом; наложение запрещено.
8. Структурные величины (ось ноги) выводятся без Δ, с пометкой «структурный».

### 14.3 Обзор «от сустава до стоп»

Строки сверху вниз: ВНЧС и мыщелки → жевательные мышцы → шея → позвоночник фронталь →
позвоночник сагитталь → таз → ось ног → стопы. Визуально сравниваются нейтраль и первая
выбранная проба; числовые колонки — до трёх проб.

### 14.4 Мастер сессии

Пошаговый, с блокировками §8.1. Шаг качества требует решения врача по каждой строке.

### 14.5 Режим тренера

Отдельная роль отображения, только чтение. Содержит: краткое заключение простым языком,
отклонения в качественной шкале, изменения в шине, статус стелек и компенсации,
программу на 12 недель с колонкой «на что смотреть», блок «чего избегать», сроки
повторного сканирования и признаки для внепланового обращения.

MUST: скрыты пороги, размеры эффекта, координаты мыщелков, микровольты, идентификаторы
правил. MUST: блок конфликтов (например, ухудшение при сжатии зубов) отображается —
он меняет выбор упражнений.

### 14.6 Темы и адаптив

MUST:
- светлая и тёмная темы плюс режим «авто» по системной настройке;
- цвета SVG-графики берутся из той же палитры и перерисовываются при смене темы;
- шкала давления имеет отдельный набор оттенков для тёмной темы;
- раскладки: компьютер (боковая навигация), планшет до 1024 (горизонтальная навигация),
  телефон до 700 (вертикальные строки обзора, таблицы с горизонтальной прокруткой без
  сокрытия колонок).

## 15. Приватность, роли, аудит

Роли: `operator`, `clinician`, `methodologist`, `coach` (только чтение своего варианта отчёта),
`admin`.

MUST:
- данные особой категории по GDPR: правовое основание и DPIA оформляются до пилота;
- ПДн не хранятся в модуле, только `patient_ref` (требования к нему — §13, Р-9);
- аудит-лог фиксирует открытие, изменение, подпись, экспорт;
- экспорт когорты обезличен, ключ соответствия хранится вне модуля;
- развёртывание on-prem поддерживается как основной сценарий.

MUST (Р-11): пациент не является субъектом записи в модуль. Данные вводит `operator`,
выводы подписывает `clinician`. Пациент получает результат только пациентским вариантом
подписанного отчёта (§13, `variant=patient`) и не имеет ни записи, ни удаления —
удаление противоречит аудиту (§15) и воспроизводимости (§4). Роль `coach` — чтение
своего варианта отчёта, без доступа к сырым величинам (§14.5).

## 16. Тестирование и приёмка

| Уровень | Обязательное покрытие |
|---|---|
| Фикстуры парсеров | реальный файл каждого формата → ожидаемый разбор |
| Property-тест знаков | зеркальный вход даёт зеркальный выход |
| Табличные тесты анализа | z, PI, effect size, оси, когерентность, комбинированная проба |
| Эталонные кейсы правил | сценарий → набор сработавших `rule_id` |
| Детерминизм | одинаковый вход и версии → одинаковый `input_hash` и `result` |
| Валидаторы протокола | каждое нарушение §8.1 блокирует переход |
| Сопоставимость визитов | несовпадение версий или опоры → Δ не вычисляется |
| Идемпотентность импорта | повторный файл не создаёт обследование |
| Работа без норм | сценарии проходят при пустых нормах; `RI` считается, `PI` — прочерк |
| Предрегистрация | подтверждающий анализ невозможен после доступа к lockbox |
| Множественность | размер семейства сравнений совпадает с числом фактически проверенных |
| Обратимость исключений | пересчёт на полном наборе даёт результат чувствительности |
| Слепота разбора качества | экран не отдаёт код пробы до фиксации решений |
| Интерфейс | каждый раздел отрисовывается; отсутствие данных даёт объяснение, а не пустой экран |
| Доступность | контраст, фокус с клавиатуры, подписи к графикам |

Критерии приёмки этапа считаются выполненными только при зелёных тестах соответствующих строк.

## 17. Этапы

**Этап 1.** Реестр параметров (`direction = unknown` по умолчанию) и знаковые соглашения.
Парсер formetric под реальный файл. Импорт с идемпотентностью и полным сохранением сырых
данных. `RI` как основной индекс; `z` и `PI` — когда нормы появятся. Журнал исключений,
именованные когорты. → работающий продукт.

**Этап 1.5 (Р-20).** Режим повторяемости: протокол test-retest, расчёт собственного SDC,
выпуск `sdc_<version>.yaml` с `source: own_repeatability`. Без собственного SDC у Этапа 2
нет опоры, а внешнего источника для этой комбинации оборудования не существует.

**Этап 2.** Мастер сессии с валидаторами, реестр проб, sham-условие, рандомизация с seed,
слепой разбор качества, эффекты и пороги, ранжирование, подтверждающий повтор, карта проб,
история с правилом сопоставимости. Предрегистрация гипотез, lockbox, контроль
множественности.

**Этап 3.** Bridge Agent. Pedoscan и нижний контур: компенсация длины ног, домен опоры,
комбинированная проба, отпечатки и карта разности.

**Этап 4.** ЭМГ: контейнер сигнала, адаптер под конкретный миограф, уровень E, метрики,
флаги качества, мышечный индекс.

**Этап 5.** Кондилография: ручной ввод, адаптеры, связка по коду пробы, когерентность,
карта отклика.

**Этап 6.** Движок правил, библиотека упражнений, стельки, прогноз, режим тренера —
только по параметрам с установленным направлением и подтверждёнными закономерностями
(Р-19). Доступен при `intended_use = clinical`.

**Этап 7.** Когортный дашборд, обезличенный экспорт, база исходов, калибровка прогноза
на собственных данных.

Порядок 1 → 1.5 → 2 фиксирован. Этапы 3–5 могут идти параллельно разными исполнителями,
поскольку опираются на общий канонический слой.

MUST (Р-14, Р-15, Р-16, Р-17): исследовательский минимум входит в Этапы 1 и 2, а не
откладывается на Этап 7. Данные, собранные без предрегистрации, журнала исключений,
фиксации рандомизации и слепой оценки качества, задним числом доказательными не станут —
они останутся пригодны только для поискового анализа. Подробности —
[исследовательский контур](./research-framework.md#12-порядок-этапов).
