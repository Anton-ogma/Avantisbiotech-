# Исследовательский контур

Дополнение к [ТЗ v1.0](./TZ-postural-module-v1.0.md). Разделы 4–12 ТЗ — контракт;
изменения к ним зафиксированы в [журнале решений](./decisions.md), Р-13…Р-20.

---

## 0. Постановка

Платформа — научно-практическая: она предназначена **выявлять** закономерности, а не
применять готовые. Комбинация оборудования (формометрия + подометрия + ЭМГ +
аксиография в общем протоколе проб) не имеет прецедента, протоколы разрабатываются
здесь же, часть проверяемых гипотез ранее отвергалась.

Из этого следует два требования, задающих всю архитектуру исследовательского контура.

**Требование 1. Ничто клинически установленное не зашивается как истина.**
Нормы, направление «лучше/хуже», пороги значимости, состав индексов, правила
рекомендаций — параметры исследования, а не константы. Каждое из них должно
поддерживать состояние «не определено» и не блокировать работу платформы своим
отсутствием.

**Требование 2. Дизайн исследования защищён программно, а не дисциплиной оператора.**
Новая закономерность отвергается внешним читателем не потому, что она неверна, а
потому, что дизайн допускает альтернативное объяснение: подбор порога после просмотра
данных, множественные сравнения, необъявленные исключения, эффект порядка проб,
неслепая оценка качества. Всё перечисленное — то, что ПО может исключить механически.
Это и есть главный вклад платформы в убедительность результата.

## 1. Методологическая рамка: серия n-of-1

Протокол проб по своей структуре — **испытание n-of-1**: пациент служит собственным
контролем, условия чередуются, между ними возвращается нейтраль. Это не аналогия, а
точное совпадение с существующим дизайном, у которого есть проработанная методология
и признанные критерии качества.

Что из этого следует практически:

| Элемент дизайна n-of-1 | Реализация в платформе |
|---|---|
| Пациент — собственный контроль | нейтраль как опора (§8 ТЗ), уже есть |
| Многократное чередование условий | повтор проб, не только подтверждающий (§8.3) |
| Рандомизация последовательности | внутри группы (§8.1.2), seed фиксируется — см. §4 ниже |
| Отмывка между условиями | `carryover_min` (§8.1.4), уже есть |
| Контроль времени и дрейфа | нейтраль ≥3 раза за сессию (§8.1.8), уже есть |
| Sham-условие | **добавляется**, см. §3 |
| Слепота оценки | **добавляется**, см. §5 |
| Агрегация серии n-of-1 в когорту | когортный слой, см. §7 |

Серия n-of-1 агрегируется в групповой вывод корректно — это установленный способ
получить обобщаемый результат без классического параллельного РКИ. Для платформы,
где каждое обследование дорого и пациентов немного, это единственная реалистичная
дорога к доказательности.

## 2. Работа без норм и без порогов

Самая жёсткая зависимость исходного ТЗ: `z` требует норм → `PI` требует `z` →
`ΔPI` требует `PI` → шорт-лист и ранжирование требуют `ΔPI`. Нет опубликованных норм
для параметра — не работает ничего.

Для исследовательской платформы это неприемлемо: норм по большинству параметров
в нужной стратификации попросту нет, а те, что есть, получены на других популяциях
и другим оборудованием — принимать их значит заранее встроить в результат чужое
допущение.

**Решение: два независимых индекса.**

| | `PI` — популяционный | `RI` — отзывчивость (response index) |
|---|---|---|
| Опора | норма популяции | собственная нейтраль пациента |
| Требует | `norms_version` | только `thresholds_version` (SDC) |
| Отвечает на вопрос | насколько далеко от нормы | насколько меняется под пробой |
| Доступен без норм | нет | **да** |

```
RI_domain = Σ_p w_p · min(|Δ_p| / SDC_p, cap)
RI        = Σ_domain W_domain · RI_domain
ΔRI       = RI(trial)   # уже относительно baseline_ref по построению
```

MUST: `RI` — основной индекс исследовательского контура; `PI` вычисляется, только когда
нормы для параметра определены, и отсутствие норм не блокирует ни один сценарий.
В отчёте и на графиках всегда указано, какой индекс используется.

MUST: параметр без норм участвует в `RI` и не участвует в `PI`; в таблицах колонка
нормы — прочерк (это ровно §14.2.5 ТЗ), а не ноль и не пропуск строки.

Это не смягчение требований, а более честная опора: метод по построению измеряет
**отклик на пробу**, а не удалённость от популяции. Популяционная норма нужна для
описания исходного состояния и не должна быть входом для оценки отклика.

## 3. Sham-условие

MUST для исследовательских протоколов: в сессии присутствует **sham-проба** — условие,
неотличимое для пациента от активного, но методически неактивное (например, аппарат
установлен без терапевтического позиционирования, клин нулевой толщины).

Без sham любое изменение позы под пробой объясняется альтернативно: время, внимание,
утомление, ожидание эффекта. Повторная нейтраль контролирует дрейф во времени, но
не контролирует сам факт вмешательства. Разница «активная проба vs sham» — то, что
переживёт внешнюю критику; разница «активная проба vs ничего» — не переживёт.

Код `CTRL_SHAM_<уровень>` добавляется в реестр проб. `role = control`.

Валидатор (блокирующий, §8.1 ТЗ): в сессии со `study_mode = true` и хотя бы одной
терапевтической пробой обязана присутствовать sham соответствующего уровня.

## 4. Порядок, рандомизация, перенос эффекта

`carryover_min` (§8.1.4 ТЗ) — это **допущение**, что за указанное время эффект
предыдущей пробы исчез. Допущение непроверенное; для нового протокола оно само
подлежит проверке.

MUST фиксировать в `sessions`:

- `randomization_scheme` — схема (`none` | `random_within_group` | `counterbalanced`);
- `randomization_seed` — целое; последовательность воспроизводима из seed;
- фактический порядок уже есть в `trials.ordinal`.

Это даёт возможность проверять эффект порядка и перенос как **гипотезу**, а не
принимать их отсутствие на веру: при накоплении сессий позиция пробы в
последовательности становится ковариатой в модели. Если перенос обнаружится,
`carryover_min` калибруется по собственным данным — как и всё остальное.

MAY: контрбалансировка порядка между пациентами — при небольшой серии даёт больше,
чем случайная рандомизация.

## 5. Слепота при оценке качества

Шаг `quality_reviewed` (§8.1 ТЗ) требует решения человека по каждой строке измерений.
Если оценивающий видит код пробы, он знает, какая проба «должна» сработать, — и
исключение артефактов становится необъявленной степенью свободы исследователя.

MUST: экран разбора качества скрывает код пробы, роль, порядковый номер и любые
результаты анализа. Оценивающий видит сигнал, флаги качества и ничего больше.
Раскрытие происходит после фиксации всех решений по сессии.

MUST: каждое исключение пишется в журнал исключений с причиной и автором и обратимо —
анализ должен уметь пересчитаться на полном наборе для проверки чувствительности
результата к исключениям. Необратимое исключение равносильно потере данных.

MAY: слепота пациента там, где физически возможна (sham-клин против активного —
возможна; наличие шины во рту — нет). Фактическая слепота фиксируется полем, а не
предполагается.

## 6. Предрегистрация и разделение поиска и подтверждения

Главный источник ложных закономерностей в этой постановке — комбинаторика:
десятки параметров × десятки проб × несколько модальностей. При таком объёме
сравнений «достоверные» находки возникают из шума неизбежно.

MUST: каждый анализ на уровне когорты выполняется в одном из двух режимов, режим
фиксируется в результате и печатается везде, где результат показывается.

**`exploratory` — поиск.**
Ограничений на число проверяемых сочетаний нет. Результат — **гипотеза**, не вывод.
MUST: любая формулировка результата поискового анализа содержит явную пометку
«поисковый анализ, требует подтверждения»; вывести её нельзя.
MUST: применяется контроль частоты ложных обнаружений (Benjamini–Hochberg) по всему
семейству проверенных сочетаний, а не по выбранным после просмотра. Число проверенных
сочетаний печатается рядом с результатом.

**`confirmatory` — подтверждение.**
MUST: гипотеза зарегистрирована **до** доступа к подтверждающим данным. Регистрация
фиксирует: формулировку, параметры и пробы интереса, направление ожидаемого эффекта,
план анализа, критерии включения в когорту, целевой размер выборки. Запись
неизменяема, хэшируется, дата фиксируется.
MUST: платформа не даёт запустить подтверждающий анализ на данных, к которым уже
был доступ у зарегистрировавшего, — см. §7 lockbox.

MUST: отклонение фактического анализа от зарегистрированного плана допускается, но
регистрируется как отклонение с причиной и печатается в результате. Молчаливое
изменение плана запрещено технически, не организационно.

## 7. Когорта, lockbox, происхождение данных

MUST: набор данных для исследования формируется как **именованная когорта** —
неизменяемый список сессий с критериями отбора и датой фиксации. Анализ ссылается
на когорту, а не на «все данные на момент запуска».

MUST: при регистрации подтверждающей гипотезы когорта делится на **рабочую часть** и
**lockbox**. Lockbox недоступен для любого анализа до момента, когда подтверждающий
анализ объявлен готовым; открытие lockbox — однократное событие с записью в аудит.
Повторный подтверждающий анализ на том же lockbox невозможен.

MUST: у каждого агрегированного результата хранится полное происхождение: когорта,
версии конфигурации (пять, Р-3), список исключений, режим, идентификатор гипотезы,
`input_hash`. Результат воспроизводится из этих данных побитово — то же требование
детерминизма, что и для сессионного анализа (§4.2 ТЗ), но на уровне когорты.

## 8. Что делать со значениями ниже порога

§9.3 ТЗ: значения ниже SDC не участвуют в ранжировании, не попадают в шорт-лист,
не порождают рекомендаций. Для **клинического** вывода это правильно и остаётся в силе.

MUST: для **исследовательского** анализа это правило не действует. Подпороговые
значения хранятся полностью, участвуют в групповых оценках и в моделях.

Обоснование существенно, поэтому явно: SDC — порог различимости **однократного
измерения у одного пациента**. Ошибка средней по группе меньше индивидуальной в
√n раз. Систематический сдвиг, неразличимый в отдельном обследовании, обнаруживается
на когорте — и именно в этой зоне лежат закономерности, которые ранее отвергались
как «в пределах погрешности». Отбрасывать подпороговые значения на входе — значит
заранее закрыть себе доступ к искомому.

Разделение проходит по типу вывода, а не по данным:

| | клинический контур | исследовательский контур |
|---|---|---|
| Подпороговые значения | не интерпретируются, нейтральный цвет | анализируются, входят в модели |
| Единица вывода | этот пациент | когорта / серия n-of-1 |
| Может стать назначением | да, после подписи врача | никогда напрямую |

## 9. Направление «лучше/хуже» — параметр исследования

`param_registry.direction` (§7 ТЗ) кодирует клиническое допущение: рост параметра
это ухудшение, снижение — улучшение или наоборот. Для параметра, по которому
закономерность только предстоит установить, такое допущение — предрешение результата.

MUST: домен `direction` расширяется значением `unknown`. Для параметра с
`direction = unknown`:

- в `RI` он входит по модулю (величина отклика), знак не интерпретируется;
- в UI изменение показывается нейтральным цветом с подписью направления, без
  «улучшение»/«ухудшение»;
- в правила рекомендаций (§11 ТЗ) он не входит вовсе;
- в отчёте помечается как параметр под изучением.

MUST: смена `direction` с `unknown` на определённое значение — изменение
`registry_version` со всеми последствиями для сопоставимости (§12 ТЗ), и требует
ссылки на результат подтверждающего анализа, который это направление установил.
Именно так новая закономерность попадает в продукт: не правкой конфигурации,
а через зарегистрированное подтверждение.

## 10. Платформа порождает собственные нормы и пороги

В исходном ТЗ нормы и SDC — внешний вход (§10, `source` обязателен). Для новой
комбинации оборудования и собственных протоколов внешнего входа не существует.

MUST: платформа поддерживает **режим повторяемости** — протокол test-retest, где
одно и то же условие измеряется повторно с переустановкой пациента, и по накопленным
парам вычисляется SDC для каждого параметра.

- Результат — файл `thresholds/sdc_<version>.yaml` с `source: own_repeatability`,
  ссылкой на когорту, числом пар, доверительным интервалом оценки.
- До появления собственного SDC платформа работает с `source: demo` и показывает
  предупреждение на всех экранах (это уже требование §10 ТЗ).

MUST: аналогично для норм — `source: own_cohort` со ссылкой на когорту, стратификацию
и число наблюдений. Собственная норма имеет тот же статус, что и литературная,
и отличается только полем `source`.

Это снимает внешний блокер: SDC-исследование перестаёт быть предварительным условием
разработки и становится первой функцией платформы. Соответственно меняется порядок
этапов — см. §12.

## 11. Модель данных: дополнения

К §4 ТЗ добавляются:

```sql
hypotheses(
  id uuid pk, statement text not null,
  params text[], probe_codes text[],
  expected_direction text,                   -- improving|worsening|any|unspecified
  analysis_plan jsonb not null,
  cohort_criteria jsonb not null,
  target_n int,
  mode text not null,                        -- exploratory|confirmatory
  registered_at timestamptz not null,
  registered_by text not null,
  plan_hash text not null,                   -- неизменяемость регистрации
  status text                                -- registered|running|completed|deviated|abandoned
);

cohorts(
  id uuid pk, name text, criteria jsonb not null,
  session_ids uuid[] not null,               -- фиксированный состав
  frozen_at timestamptz not null,
  lockbox_session_ids uuid[],                -- отложенная часть
  lockbox_opened_at timestamptz,             -- однократно
  hypothesis_id uuid
);

cohort_analyses(
  id uuid pk, cohort_id uuid fk, hypothesis_id uuid fk,
  mode text not null,                        -- exploratory|confirmatory
  norms_version text, thresholds_version text, rules_version text,
  profile_version text, registry_version text,
  comparisons_tested int not null,           -- размер семейства для FDR
  fdr_method text, fdr_q numeric,
  exclusion_set_hash text not null,
  deviations jsonb,                          -- отклонения от плана с причинами
  input_hash text not null,
  result jsonb, created_at timestamptz
);

exclusions(
  id uuid pk, session_id uuid fk, entity text, entity_id uuid,
  reason_code text not null, reason_text text,
  decided_by text not null, decided_at timestamptz,
  blinded boolean not null,                  -- принято ли решение вслепую
  reverted_at timestamptz                    -- исключения обратимы
);
```

К `sessions` добавляются `randomization_scheme`, `randomization_seed`,
`patient_blinded boolean`, `operator_blinded boolean`.

Инварианты:

1. `hypotheses` и `cohorts` — только вставка; изменение состава когорты создаёт новую.
2. `cohorts.lockbox_opened_at` устанавливается однократно и необратимо.
3. `cohort_analyses.input_hash` включает состав когорты, набор исключений и пять
   версий конфигурации; тот же вход даёт тот же результат.
4. Подтверждающий анализ невозможен, если `hypotheses.registered_at` позже первого
   обращения к данным lockbox.

## 12. Порядок этапов

Исходный §17 ТЗ помещает исследовательский режим в Этап 7 — последним. Для
научно-практической платформы это ошибка порядка: данные, собранные на этапах 1–6
без предрегистрации, журнала исключений, фиксации рандомизации и слепой оценки
качества, **не станут** пригодными для доказательного вывода задним числом. Их можно
будет использовать только как поисковые.

MUST: исследовательский минимум входит в Этап 1 и Этап 2.

| Этап | Добавляется из исследовательского контура |
|---|---|
| **1** | `RI` как основной индекс; `direction = unknown`; полное сохранение сырых данных; журнал исключений; когорты |
| **1.5 (новый)** | **режим повторяемости → собственный SDC**; без него Этап 2 не имеет опоры |
| **2** | sham-проба; рандомизация с seed; слепой разбор качества; предрегистрация; lockbox; FDR |
| 3–5 | без изменений |
| **6** | движок правил работает только по параметрам с установленным направлением и подтверждёнными закономерностями |
| **7** | остаётся: когортный дашборд, экспорт, база исходов — но уже на готовом фундаменте |

Этап 1.5 — не задержка, а перенос: SDC-исследование в исходном плане было внешним
блокером Этапа 2 с неопределённым сроком. Здесь оно становится функцией платформы
с понятным содержанием.

## 13. Рекомендации в исследовательском контуре

§11 ТЗ описывает движок правил, выдающий терапевтические рекомендации. Для платформы,
которая не опирается на готовые решения в лечении, это преждевременно.

MUST: развёртывание имеет явный режим назначения — `intended_use ∈ {research, clinical}`.

**`research`:** движок правил отключён; платформа выдаёт наблюдения, отклики и
статистику, но не терапевтические назначения. Отчёт содержит измеренное и найденное,
не предписанное.

**`clinical`:** движок правил работает, но **только** по параметрам с установленным
`direction` и закономерностями, прошедшими подтверждающий анализ. Правило, опирающееся
на параметр с `direction = unknown` или на неподтверждённую закономерность, не
загружается — валидация конфигурации при старте (§10 ТЗ) отклоняет такой файл.

Это и есть механизм, которым результат исследования становится продуктом: правило
нельзя написать раньше, чем закономерность подтверждена, — не по регламенту, а
технически.

Регуляторная сторона: режим `research` не выводит платформу из-под требований §15
(аудит, версионирование, воспроизводимость) — они для исследования нужны не меньше.
Но отсутствие терапевтического вывода существенно меняет разговор о MDR, поэтому
границу между режимами следует зафиксировать в документации до пилота.
